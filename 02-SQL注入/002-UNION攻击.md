## 一、漏洞原理

`UNION` 会把两条 SELECT 的结果**纵向合并**成一个结果集 —— 这是借注入点读其它数据的入口。

但数据库对 UNION 有一条硬性要求：**前后两个查询的列数必须一致**，对不上就直接报错。所以 UNION 注入的第一步永远是：**问出原查询返回几列**。

判断方法：把 `UNION SELECT NULL[, NULL...]` 接在注入点后面，`NULL` 的个数从 1 开始递增，直到页面**不再报错** —— 那一刻的 `NULL` 个数就是列数。

**为什么用 `NULL` 而不是具体值？** `NULL` 与任何数据类型都兼容，不会因为类型不匹配而干扰判断。这样报错信息就只反映**列数**这一个变量。

## 二、复现步骤

1. Burp 抓到 `category=Accessories` 这个请求
2. 先补 `'` 闭合字符串，再接 UNION：

```
category=Accessories' UNION SELECT NULL--
```

→ 页面报错（列数不匹配）

3. 逐个增加 `NULL`，每次放行观察：

| 试的次数 | payload | 响应 |
|---|---|---|
| 第 1 次 | `' UNION SELECT NULL--` | 错误 |
| 第 2 次 | `' UNION SELECT NULL,NULL--` | 错误 |
| 第 3 次 | `' UNION SELECT NULL,NULL,NULL--` | **正常返回** |

4. 结论：**原查询返回 3 列**

**关键点**：这一次的「成功」只意味着**不报错**，页面上看不出任何变化 —— 因为三个位置都是 `NULL`，什么都不显示。判断列数靠的是「报错 / 不报错」这个二元信号，而不是回显内容。

## 三、根本原因

与前题同源：注入点让刻意构造的 UNION 语句进入了原查询。

但这题额外暴露了**报错信息泄漏**的问题：数据库把「列数不匹配」这类内部结构错误直接返回给用户，等于给攻击者提供了一个免费的结构探针。

关掉详细错误回显能显著提高门槛（把攻击逼向盲注），但**治不了根** —— 根源仍是用户输入被当作 SQL 执行。

## 四、修复方案

1. **参数化查询** —— 同 001，根治
2. **关闭详细错误回显** —— 给用户统一错误页，数据库报错只写进服务端日志。纵深防御，不能替代参数化
3. **数据库账号最小权限** —— 即便被注入，也读不到敏感表

## 五、面试问答

**Q：判断列数有几种方法？**
A：① `UNION SELECT NULL` 递增，通用、最稳；② `ORDER BY N` 递增，从 1 试到报错，报错前的数字就是列数，更快但依赖 ORDER BY 可用。两者都能在盲注场景下靠报错／响应差异判断。

**Q：为什么从 1 开始递增，不从大数往下试？**
A：都可以，但递增能在报错前拿到**确切值**；递减只能确定一个上界。

**Q：知道列数之后为什么还要继续试？**
A：因为 UNION 的每个位置还有类型约束，得能容纳**字符串**才能读出文本数据（用户名、密码都是字符串）。数字列塞字符串会报错。
