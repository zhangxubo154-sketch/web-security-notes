## 一、漏洞原理

登录功能在服务端拼出类似这样的查询：

```sql
SELECT * FROM users WHERE username = 'administrator' AND password = '输入的密码'
```

代码的判断逻辑通常是：**这个查询只要能返回一行，就认为登录成功。**

而 `username` 是用户可控的，且被直接拼进 SQL。所以在用户名里补一个单引号闭合字符串、再加注释符 `--`，就能把**口令校验整段注掉**：

```sql
SELECT * FROM users WHERE username = 'administrator'--' AND password = '任意内容'
                                                   ↑ 从这里之后全被注释
```

结果等价于：

```sql
SELECT * FROM users WHERE username = 'administrator'
```

**查询会返回 administrator 那一行 → 登录成功，且完全不需要知道口令。**

口令字段留空、随便填、填错都可以 —— 它根本没参与查询。

## 二、复现步骤

1. 打开登录页，随便填一组账号口令提交，用 Burp 抓包
2. 定位 `username` 参数
3. 改为：

```
username=administrator'--&password=任意
```

4. 放行请求 → **以 administrator 身份登录成功**，进入后台

**关键点**：这次攻击**不需要任何数据库知识**。不知道表名、列名、数据内容，只靠一次字符串操作就拿到了管理员会话。

## 三、根本原因

与前几题同源（用户输入被拼进 SQL），但危害性质**不同**：

| | 001 / 002 / 003 / 004 | 005（本题） |
|---|---|---|
| 攻击性质 | **信息泄露** —— 读到本不该读的数据 | **认证绕过** —— 直接获得权限 |
| 需要什么 | 知道列数、列类型、表名、列名 | **什么都不需要**，一次请求 |
| 直接后果 | 需要再拿数据去登录 | 拿到管理员操作权限 |

这是**危害等级最高、成本最低**的一类注入：它不读数据，直接改**程序的判断逻辑**。

**一句话根因**：认证决策建立在"这条 SQL 有没有返回行"之上，而这个 SQL 又允许用户输入改写自己的结构。等于把门锁的判定权交给了进门的人。

## 四、修复方案

1. **参数化查询** —— 输入作为值传入，`--` 只是普通字符，无法改变语句结构。**根治**
2. **口令哈希存储 + 恒定时间比较** —— 减小库被读走后的影响
3. **登录失败节流 / 锁定** —— 限制爆破与异常尝试
4. **不要在认证逻辑里做"查得到就算通过"** —— 应显式校验口令哈希是否匹配，而不是依赖"有没有返回行"
5. **多因素认证（MFA）** —— 即使口令被绕过，还有第二道门

## 五、面试问答

**Q：SQL 注入绕过登录的原理？**
A：用户名被拼进查询，用 `'--` 注掉口令校验部分，使查询只按用户名匹配并返回该行，程序据此判定登录成功。

**Q：`admin'--` 和 `' OR 1=1--` 有什么区别？**
A：`admin'--` 精确指定以某个账号登录；`' OR 1=1--` 让条件恒真，返回的通常是**表里第一行** —— 未必是管理员。所以想拿管理员权限，前者更可控。

**Q：为什么说这是最危险的注入类型？**
A：它不需要知道任何库结构或数据，一次请求即可能获得最高权限。相比"读到数据再想办法利用"，它直接改变认证逻辑。

**Q：参数化查询为什么能防住？**
A：语句结构先编译固定，输入只作为数据传入。`--`、`'` 都只是普通字符，无法改变 SQL 语义。

**Q：除了参数化查询还能做什么？**
A：口令哈希存储、登录节流、显式校验哈希而非依赖返回行数、MFA。这些是纵深防御，不能替代参数化查询。
