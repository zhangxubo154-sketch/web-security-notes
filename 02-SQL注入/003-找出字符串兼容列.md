## 一、漏洞原理

知道列数（3 列）之后还**读不出数据** —— 因为 UNION 的每个位置都有**数据类型**约束。

数据库的列是有类型的（数字、字符串、日期…）。往数字类型的列里塞字符串，数据库直接报类型错误。而我们要读的用户名、密码、版本号**全是字符串**，所以必须先找出**哪一列能容纳字符串**。

判断方法：把已知列数里的 `NULL` **逐个换成字符串** `'a'`，哪个位置不报错，哪个位置就是字符串兼容列。

**为什么先试 `'a'` 而不是题目给的字符串？** 先用一个随便的短串做**类型探测**，确认哪列可用；确定之后才换成真正的目标串。两步分开，出错时能立刻定位是「列不对」还是「串不对」。

## 二、复现步骤

**第一段：确认列数**（上一题结论）

```
category=Accessories' UNION SELECT NULL,NULL,NULL--
```
→ 正常返回，确认 3 列

**第二段：逐列试字符串**

| payload | 响应 | 结论 |
|---|---|---|
| `' UNION SELECT 'a',NULL,NULL--` | 500 报错 | 第 1 列不是字符串类型 |
| `' UNION SELECT NULL,'a',NULL--` | **200 正常，页面多出一行 `a`** | **第 2 列是字符串类型 ✅** |
| `' UNION SELECT NULL,NULL,'a'--` | 500 报错 | 第 3 列不是字符串类型 |

**第三段：替换成题目指定的随机串**

题目会给一个随机字符串（形如 `JyHk0h`，每次开实例都不同），要求让它出现在响应里：

```
category=Accessories' UNION SELECT NULL,'JyHk0h',NULL--
```

→ 页面横幅变为 **Solved**，过关。

**关键点**：`'a'` 放在第 2 列时，页面真的渲染出了多出来的那一行 —— 这一下同时证明了两件事：**第 2 列是字符串列**，且**第 2 列的内容会显示在页面上**（即回显位）。

## 三、根本原因

前两题的根因延续（用户输入被当 SQL 执行），这题多暴露了一层：

**数据库会「回答」攻击者的类型提问。** 类型不匹配时的报错信息，等于告诉攻击者这一列是什么类型。再叠加**详细错误回显**，攻击者就能以零成本摸清表结构。

如果应用把错误全部吞掉（永远返回同一个页面），这题就得换思路 —— 用**布尔盲注**：靠页面渲染是否正常／内容是否变化来逐位猜出类型和内容。速度慢很多，但依然可行。

## 四、修复方案

1. **参数化查询** —— 正本清源
2. **关闭详细错误回显** —— 让类型错误不再反馈给攻击者，把攻击从「报错型」逼成「盲注型」，大幅提高攻击成本
3. **数据库账号最小权限** —— 即使注入成功，也读不到敏感表

## 五、面试问答

**Q：知道列数为什么还不够？**
A：UNION 的每个位置有类型约束，数字列塞不进字符串。而敏感数据（用户名／密码）都是字符串，必须先定位字符串兼容列。

**Q：怎么判断一列是不是字符串类型？**
A：往该位置塞字符串，看是否报类型错误。不报错即兼容。用 `NULL` 做基线是因为它跟所有类型都兼容。

**Q：`UNION SELECT NULL,...` 里为什么必须用 NULL？**
A：`NULL` 是唯一能保证「不因类型问题报错」的值，这样报错就只反映列数，排除类型干扰。

**Q：如果响应里完全不显示任何回显内容呢？**
A：UNION 就失效了，得换盲注（布尔盲注／时间盲注），通过页面差异或响应延迟逐字符推断数据。

**Q：`--` 注释有什么坑？**
A：MySQL 里 `--` 后必须跟空格或换行才是注释，URL 里通常写 `--+` 或 `--%20`；MySQL 还支持 `#` 作行注释。
